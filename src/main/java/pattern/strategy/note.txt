🎯 场景说明
假设我们正在开发一个电商系统，需要支持多种支付方式（如支付宝、微信、信用卡）。

不同支付方式的处理逻辑不同，但对外暴露的接口一致。

策略模式非常适合这种“相同目的、不同实现”的场景。

✅ 策略模式核心组成
策略接口（Strategy Interface）：定义所有支持算法的公共接口。
具体策略类（Concrete Strategies）：实现策略接口，提供具体算法。
上下文类（Context）：持有一个策略引用，负责与客户端交互，并将请求委托给具体策略。

✅ 策略模式的优点
开闭原则：新增支付方式只需实现 PaymentStrategy，无需修改上下文。
消除条件语句：避免大量 if-else 或 switch 判断支付类型。
算法可复用、可测试：每个策略独立，便于单元测试。
运行时动态切换策略：用户可自由选择支付方式。
📌 适用场景
多种算法/行为可互换（如排序算法、压缩算法、验证规则等）。
需要在运行时动态选择行为。
避免使用多重条件判断导致代码臃肿。
💡 提示：在 Spring 等框架中，策略模式常结合 @Component 和 Map<Class, Strategy> 实现自动注入和策略路由，进一步提升扩展性。

这个实现展示了策略模式的核心思想：将变化的行为封装起来，让它们可以互相替换，使算法的变化独立于使用它的客户端。
