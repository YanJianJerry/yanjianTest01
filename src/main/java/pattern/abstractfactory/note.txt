🎯 场景说明
假设我们正在开发一个跨平台 UI 框架，需要支持不同操作系统的原生界面风格：

Windows 风格：按钮、复选框都使用 Windows 样式
Mac 风格：按钮、复选框都使用 macOS 样式
关键要求：同一界面中所有组件风格必须一致，不能混用（如不能 Windows 按钮 + Mac 复选框）。

这正是 抽象工厂模式 的典型应用场景——创建一组相关或相互依赖的对象，而无需指定它们的具体类。

✅ 抽象工厂模式结构组成
抽象产品（Abstract Products）：定义每类产品的接口（如 Button, Checkbox）。
具体产品（Concrete Products）：实现抽象产品接口（如 WindowsButton, MacCheckbox）。
抽象工厂（Abstract Factory）：声明创建所有产品的方法（如 createButton(), createCheckbox()）。
具体工厂（Concrete Factories）：实现抽象工厂，返回同一风格的具体产品（如 WindowsFactory, MacFactory）。

🔑 抽象工厂模式的核心特点
1. 创建产品族（Product Family）
不是创建单一对象，而是创建一组相关或依赖的对象。
所有对象属于同一“主题”或“平台”（如 Windows 套件、Mac 套件）。
2. 保证产品的一致性
避免客户端混用不同风格的组件（如 Windows 按钮 + Mac 复选框）。
由具体工厂确保返回的产品是兼容的。
3. 高度解耦
客户端只依赖抽象工厂和抽象产品接口。
新增产品族（如 Linux 风格）只需新增具体工厂和产品类，无需修改客户端代码。
4. 符合开闭原则
✅ 对扩展开放：可轻松添加新的产品族（如 LinuxFactory）。
❌ 对修改关闭：但新增产品种类（如添加 TextBox）需修改所有工厂接口和实现类。
5. 组合多个工厂方法
抽象工厂内部通常包含多个工厂方法（createButton(), createCheckbox()）。
可看作“工厂方法的集合”。
⚠️ 适用场景 vs 不适用场景
✅ 适用场景：
系统需要独立于产品的创建、组合和表示。
系统要配置成使用多个产品族之一。
相关产品需要一起使用，且必须保持兼容（如 UI 套件、数据库驱动套件）。
❌ 不适用场景：
只需要创建单一类型对象 → 用工厂方法模式更简单。
产品种类经常变化 → 抽象工厂难以扩展（需改接口）。
🆚 与工厂方法模式对比
特性	工厂方法	抽象工厂
创建对象数量	1 种	多种（产品族）
扩展产品实现	容易	容易
扩展产品种类	困难	困难
复杂度	低	中高
典型应用	日志器、支付方式	跨平台 UI、游戏主题包
💡 总结
抽象工厂模式 = 产品族的工厂

它通过一个统一的工厂接口，确保创建出的对象是语义一致、风格统一、相互兼容的，是构建可扩展、可维护系统的重要工具。

该模式在大型框架（如 Java AWT、Spring、游戏引擎）中广泛应用，是设计高质量软件架构的基石之一。
