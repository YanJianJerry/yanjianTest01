🎯 场景说明
假设我们开发一个跨平台的图形界面应用，需要在不同操作系统（如 Windows、macOS）上创建原生风格的按钮。

Windows 上显示为“Windows 按钮”
macOS 上显示为“Mac 按钮”
工厂方法模式允许子类决定实例化哪个类，从而将对象的创建延迟到子类。

✅ 工厂方法模式核心组成
产品接口（Product）：定义所有产品对象的公共接口（如 Button）。
具体产品类（Concrete Products）：实现产品接口的不同变体（如 WindowsButton, MacButton）。
创建者类（Creator）：声明工厂方法（返回产品接口），可包含通用逻辑。
具体创建者类（Concrete Creators）：重写工厂方法，返回具体产品实例（如 WindowsDialog, MacDialog）。
✅ 工厂方法模式的优点
解耦对象创建与使用：客户端不关心具体产品类。
符合开闭原则：新增产品（如 LinuxButton）只需添加新工厂和产品类，无需修改现有代码。
支持多态创建：不同子类可返回不同类型的产品。
便于单元测试：可轻松替换为 Mock 工厂。
📌 与简单工厂的区别
特性	简单工厂	工厂方法
是否符合开闭原则	❌（新增产品需修改工厂）	✅（通过继承扩展）
创建逻辑集中	是	分散到子类
设计复杂度	低	中等
适用场景	产品类型少且稳定	产品类型多或需扩展
🚀 扩展建议
可结合 配置文件 或 注解 动态选择工厂。
在 Spring 中，可通过 @Conditional 或工厂 Bean 实现类似逻辑。
若产品族复杂（如同时创建按钮、文本框、菜单），可升级为 抽象工厂模式。
这个实现展示了工厂方法模式的核心思想：定义一个用于创建对象的接口，但让子类决定实例化哪个类。工厂方法使一个类的实例化延迟到其子类。




工厂方法模式（Factory Method Pattern）是一种经典的创建型设计模式，其核心思想是将对象的创建延迟到子类，从而实现“依赖抽象，而非具体实现”和“对扩展开放，对修改关闭”（开闭原则）。

在实际开发中，工厂方法模式被广泛应用于各种框架、库和企业级系统中。以下是几个经典且权威的应用案例：

✅ 1. Java 标准库中的 Calendar.getInstance()
java
编辑
Calendar cal = Calendar.getInstance();
说明：
Calendar 是一个抽象类（相当于 Creator）。
getInstance() 是一个静态工厂方法（虽非严格意义上的工厂方法模式，但思想一致）。
实际返回的是 GregorianCalendar 等具体子类（Concrete Product），具体类型由系统时区、地区等决定。
为什么是工厂方法？
客户端无需知道具体日历实现类。
不同地区/语言环境可返回不同实现（如 BuddhistCalendar、JapaneseCalendar 等）。
💡 注：严格来说，getInstance() 是静态工厂方法，但其设计意图与工厂方法模式高度一致，常被作为教学案例。

✅ 2. Java 中的 NumberFormat.getInstance()
java
编辑
NumberFormat nf = NumberFormat.getInstance(Locale.US);
返回 DecimalFormat 或其他本地化格式化器。
客户端通过 Locale 参数间接选择具体实现，而无需 new DecimalFormat()。
符合“创建逻辑封装 + 多态返回”的工厂思想。
✅ 3. JDBC 中的 DriverManager.getConnection()（间接体现）
虽然 JDBC 主要使用服务提供者接口（SPI），但其驱动加载机制体现了工厂思想：

java
编辑
Connection conn = DriverManager.getConnection(url, user, pwd);
不同数据库（MySQL、PostgreSQL）提供自己的 Driver 实现。
DriverManager 内部根据 URL 选择合适的驱动并创建 Connection。
每个数据库厂商的驱动类（如 com.mysql.cj.jdbc.Driver）可视为一个“具体工厂”。
🔍 更准确地说，这是服务定位器 + 工厂的结合，但核心仍是“根据条件创建不同产品”。

✅ 4. Spring Framework 中的 BeanFactory 和 ApplicationContext
java
编辑
ApplicationContext context = new ClassPathXmlApplicationContext("beans.xml");
UserService userService = context.getBean(UserService.class);
BeanFactory 是一个工厂接口（Creator）。
具体实现如 DefaultListableBeanFactory 负责创建 Bean（Product）。
用户通过配置（XML/注解）决定创建哪个类的实例，而无需 new。
Spring 容器本身就是一个高度泛化的工厂方法系统。
🌟 Spring 的 FactoryBean 接口更是工厂方法模式的直接体现：

java
编辑
public interface FactoryBean<T> {
    T getObject() throws Exception; // 工厂方法
    Class<?> getObjectType();
}
✅ 5. 日志框架中的 LoggerFactory.getLogger()（如 SLF4J + Logback）
java
编辑
Logger logger = LoggerFactory.getLogger(MyClass.class);
LoggerFactory 是工厂类。
根据绑定的具体实现（Logback、Log4j 等），返回不同类型的 Logger 实例。
应用代码不依赖具体日志实现，实现了解耦。
✅ 6. UI 框架中的跨平台组件创建（如 AWT/Swing）
虽然现代 Java UI 多用 JavaFX，但早期 AWT 中有类似设计：

java
编辑
Button button = new Button("Click"); // 实际由平台本地 peer 创建
AWT 组件在不同操作系统上由本地对等体（peer）实现。
创建逻辑由系统决定，用户只操作抽象接口。
这更接近抽象工厂模式，但其组件创建过程体现了工厂方法的思想。

✅ 7. 游戏开发中的角色/敌人生成系统
java
编辑
abstract class EnemyFactory {
    public abstract Enemy createEnemy();
}

class ForestEnemyFactory extends EnemyFactory {
    public Enemy createEnemy() { return new Goblin(); }
}

class DesertEnemyFactory extends EnemyFactory {
    public Enemy createEnemy() { return new Scorpion(); }
}
根据关卡类型动态创建不同敌人。
新增敌人类型只需新增工厂子类，符合开闭原则。
📌 总结：工厂方法模式的典型应用场景
场景	说明
框架设计	允许用户扩展产品而不修改框架代码（如 Spring）
跨平台开发	根据运行环境创建不同实现（如 UI 组件、文件系统）
插件/模块化系统	动态加载并创建模块实例
复杂对象创建	封装初始化逻辑（如数据库连接、网络客户端）
依赖解耦	客户端只依赖接口，不依赖具体类
🔚 结语
工厂方法模式的价值不在于“创建对象”，而在于将“决定创建什么”的权力交给子类或配置，从而实现高内聚、低耦合、易扩展的系统架构。上述经典案例都体现了这一设计哲学。










工厂方法模式（Factory Method Pattern）和抽象工厂模式（Abstract Factory Pattern）都是创建型设计模式，用于解耦对象的创建与使用，但它们在目的、结构和适用场景上有本质区别。

下面从多个维度清晰对比两者的不同：

🧩 1. 核心目的不同
模式	核心目的
工厂方法模式	创建单一类型的产品，但允许子类决定具体创建哪一个实现类。
抽象工厂模式	创建一组相关或依赖的产品族（Product Family），确保这些产品属于同一主题或平台。
✅ 简单说：

工厂方法：一个产品，多种实现（如“按钮”有 Windows 按钮、Mac 按钮）。
抽象工厂：多个产品，统一风格（如“UI 套件”包含按钮 + 文本框 + 菜单，全部是 Windows 风格或全部是 Mac 风格）。
🏗️ 2. 结构对比
🔹 工厂方法模式结构
java
编辑
// Creator
abstract class Dialog {
    abstract Button createButton(); // 工厂方法（返回单一产品）
    void render() { Button b = createButton(); ... }
}

// Concrete Creator
class WindowsDialog extends Dialog {
    Button createButton() { return new WindowsButton(); }
}
一个工厂方法 → 创建一个产品
🔹 抽象工厂模式结构
java
编辑
// Abstract Factory
interface GUIFactory {
    Button createButton();      // 创建按钮
    Checkbox createCheckbox();  // 创建复选框
}

// Concrete Factory
class WindowsFactory implements GUIFactory {
    Button createButton() { return new WindowsButton(); }
    Checkbox createCheckbox() { return new WindowsCheckbox(); }
}

class MacFactory implements GUIFactory {
    Button createButton() { return new MacButton(); }
    Checkbox createCheckbox() { return new MacCheckbox(); }
}
一个工厂 → 创建多个相关产品
📦 3. 产品维度不同
模式	产品维度
工厂方法	一维：只关注一种产品类型（如 Button）
抽象工厂	二维：关注多个产品类型，且它们构成一个“产品族”（如 Button + Checkbox + TextBox）
🌰 举例：

工厂方法：只管“创建什么按钮”。
抽象工厂：确保“按钮、文本框、下拉框”都是同一操作系统风格，避免混搭（如不能 Windows 按钮 + Mac 文本框）。
🔁 4. 扩展性对比
场景	工厂方法	抽象工厂
新增产品实现（如新增 LinuxButton）	✅ 容易：只需新增一个 Concrete Creator（LinuxDialog）	✅ 容易：新增一个 Concrete Factory（LinuxFactory）
新增产品类型（如新增 TextBox）	❌ 困难：需修改所有 Creator 子类（违反开闭原则）	❌ 困难：需修改所有 Factory 接口及其实现类
💡 两者在“新增产品族”时都容易扩展，但在“新增产品种类”时都难以扩展——这是抽象工厂的固有局限。

🧪 5. 经典应用场景
模式	典型场景
工厂方法	- 日志记录器（FileLogger / DBLogger）
- 支付方式（Alipay / WeChatPay）
- JDBC 中的 Driver 加载
抽象工厂	- 跨平台 UI 组件库（Windows/Mac/Linux 套件）
- 游戏中的主题资源包（现代/中世纪/科幻风格的武器+盔甲+载具）
- 数据库访问层（MySQL/PostgreSQL 的 Connection + Statement + ResultSet 组合）
🆚 对比总结表
特性	工厂方法模式	抽象工厂模式
创建对象数量	单一产品	产品族（多个相关产品）
核心接口方法数	1 个工厂方法	多个工厂方法
耦合度	低（客户端依赖产品接口）	更低（客户端依赖工厂接口 + 多个产品接口）
扩展方向	扩展产品实现（垂直）	扩展产品族（水平）
复杂度	简单	较复杂
是否包含工厂方法	是	是（抽象工厂由多个工厂方法组成）
✅ 抽象工厂 = 多个工厂方法的组合

🧱 代码示例对比（简化版）
工厂方法：只创建按钮
java
编辑
abstract class ButtonFactory {
    abstract Button createButton();
}
抽象工厂：创建整套 UI
java
编辑
interface UIFactory {
    Button createButton();
    Checkbox createCheckbox();
    TextBox createTextBox();
}
✅ 如何选择？
如果你只需要创建一种对象的不同变体 → 用 工厂方法模式。
如果你需要创建一组协同工作的对象，且它们属于同一主题/平台 → 用 抽象工厂模式。
💡 一句话记住区别：
工厂方法关注“造什么”（单个产品），

抽象工厂关注“配套造什么”（产品家族）。

两者都是优秀的设计模式，关键在于根据业务需求选择合适的抽象粒度。
